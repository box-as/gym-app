# RepState: accurate volume and flexible workout dates

## What changed

Volume bars now measure completed prescribed sets against the actual prescriptions for the selected week, rather than fixed Block 1 reference ranges or the largest muscle-group target. Every prescribed set with positive reps produces 100% completion for its muscle group. Cut and deload prescriptions use their own targets. Blank and load-only sets do not count as completed; extra sets are shown separately and cannot hide missing prescribed sets.

Session dates can be saved independently of the planned-day tabs. Keep Tuesday's workout on Tuesday's tab, set its session date to Wednesday, and change Wednesday/Thursday/Friday workout dates individually to Thursday/Friday/Saturday. **Today** is a shortcut; **Save date** explicitly saves the selected date. The overview displays the session dates. Clearing a custom date restores its scheduled fallback. Date fields now have the same sync focus protection as workout fields so background sync does not redraw the form while the date is being edited.

## Existing data and features

The training program, exercise order and log IDs, server, account/session logic, SQLite schema, Dockerfile, and Compose volume configuration are unchanged. Existing sync payloads retain their format, including `sessionDates` and per-record sync timestamps. No user data migration is required.

The revised plan/reference, extra-set logging, deletion and Undo, and previous-week weights/reps are preserved. Current public main (`26f6d37f7cbc56bce28da777a6e16a3a53b955ad`) already included those earlier updates and matched the live frontend before this patch. The October 15 source ZIP matched that baseline.

## Deploy safely

1. Back up the existing production SQLite database using a consistent SQLite backup (or an existing verified backup workflow). Keep that backup private. A browser JSON export is useful but is not a full account/database backup.
2. Apply this bundle's source changes to **the existing** `box-as/gym-app` repository on `main`, using your own authorized repo-only access. The application change is in `public/app.js`; README, update notes, and tests accompany it. Do not replace the program data or server with an older release.
3. Let the existing Coolify resource auto-deploy, or redeploy that same resource after verifying it points to the updated commit. Preserve its existing persistent mount to `/data`, environment variables, domain, and account configuration. Do not create a new resource/volume, remove a volume, run `docker compose down -v`, or overwrite `repstate.sqlite3` with anything from development.
4. Check `/api/healthz`, refresh the browser, sign in with an existing account, and confirm its prior logs remain. Verify Tuesday's tab accepts a Wednesday date and the remaining session dates can extend through Saturday. Verify a fully logged week's volume bars show 100%.

The complete source archive deliberately excludes databases, account data, tokens, keys, caches, and local test data.

## Run the checks locally

```sh
node --check public/app.js
node tests/repstate_frontend.test.js
python3 tests/server_integration_test.py
```

The frontend tests exercise the current source in an isolated JavaScript context. The server tests use disposable local accounts and a temporary database to check sync round-trips, account isolation, revision conflicts, and restart persistence. No live account is used.
